# Panel and dialogue runbook

## Freeze the inputs

Record audience and selection rules, seed or selection manifest, weights if any, a fixed observation cutoff, model identity, question wording, option order, allowed changes and answer language. Preserve each accepted generation. Use a diverse quota panel to hear contrasting views; use a probability sample or justified weights only when asked for a share of a defined population. Do not present a quota panel's raw split as that population's result.

Build each persona from a short evidence ledger, not an invented biography. Separate durable habits, recent state and task-relevant episodes; keep the scenario's assumed conditions separate from these facts. Include unknowns only when material. A public reference can suggest profile structure or provide fictional scenario diversity; don't treat it as a local population prior. Supply neutral wording and symmetric options, including familiar behavior where relevant. Do not tune a run to reach a desired response split. Require a forced choice only when requested; otherwise preserve uncertainty or conditional answers.

## Execute and continue

If `Product Rehearsal Lab` is available, use the verified project README and its actual commands: `plan` routes, `discover` lists metadata candidates, `probe` checks mapped view access without customer rows, and `run` generates replies with the selected installed local model. Its shipped demo runs on invented local databases. A working metadata probe does not prove the full company-backed run. A different runner is fine if it enforces the same data and output boundary.

Use first-person, task-specific replies. Keep responses natural without adding unobserved experiences or motives as facts. Retain earlier successful turns and apply only the named condition changes. Starting a new product, changing a panel, or changing a model is a new version; do not claim it is an exact continuation. Production-like flows use isolated tools or mocks, never actual orders, transfers, applications or customer contacts.

For long runs, prefer a runner with durable per-agent/turn receipts, exact model/config fingerprints and a single active worker. Retry only a failed or missing turn when the runner can prove the same agent, prompt, state and settings and preserve the original attempt. If it cannot, report incomplete coverage or run a separately named generation when authorized; do not replay completed agents silently. The basic Lab CLI's JSON output is not a durable per-turn resume ledger.

## Interpret the output

Check answer schema, allowed choices, evidence references, explicit condition changes and prose for scope errors: app use is not onboarding completion; holding one product does not mean holding another; a preference is not an action. A known key in the output is not proof the sentence citing it is true.

Keep panel counts and any weighted view separate. State eligible, completed and failed counts, and which denominator drives each share. For instance, if groups have 48/80 and 6/20 choices with 4 and 3 unknowns and population weights of 20% and 80%, the raw known-choice share over the original panel is 54/100. The weighted known-choice share is 36%, and weighted unknown share is 13%; treating all unknowns as that choice gives an upper bound of 49%. These are not national uptake or a confidence interval. If reporting among valid answers, use the valid-answer denominator and label the change.
