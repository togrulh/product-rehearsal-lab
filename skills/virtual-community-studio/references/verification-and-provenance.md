# Verification, comparison and provenance

## Review the decisive claim

First check the run card against the artifact, then review the failure most likely to change the conclusion: a bad join, a late fact, an invented assertion, a changed condition, a dropped response or the wrong denominator. For read-only work, don't rerun paid, sensitive or external workflows solely to decorate the report. Record which check actually ran, what failed, and what remains unverified. A separate reviewer can be useful when authorized; label a second pass by the same operator accurately. Do not start an orchestration service or agent swarm implicitly.

When asked to choose between two methods, pin identical audience, cutoff, conditions, answer constraints and acceptance checks; set a tie-breaker before seeing outputs. Use a falsifying example, not just a nicer explanation. When the user asks for validation, separate execution coverage, consistency with admitted evidence, population fidelity and agreement with independent outcomes. Use untouched labels and report the simplest relevant baseline. Results already seen during design are retrospective. Do not claim an improvement when the relevant test was not run. This is optional validation of the tool, not a trigger to run a live A/B test.

## Portable package boundary

Ship original workflow text, schemas, runnable toy examples and source links. Use invented examples independent of private data. Exclude private mappings, exports, prompts with customer evidence, ledgers, credentials, internal notes, trained weights and real cohorts even if their IDs are hashed. Verify the actual archive contents; before any separately authorized publication also verify repository history and license/ownership scope. Do not paraphrase third-party instructions to conceal copying. If including licensed third-party material, verify the exact source/version and redistribution terms and retain required notices. This skill includes no third-party files, datasets, weights or runtime dependencies.

## Method references, not dependencies

- **Local practice:** Virtual Community source routing and historical validation inform grain, availability and protected identities. Orchestration and analytics review patterns inform the run card and independent checks. Comparing methods under equal conditions and focused specialist review inform the optional comparison, not automatic delegation.
- [NVIDIA Nemotron Personas](https://huggingface.co/datasets/nvidia/Nemotron-Personas-USA) and [NeMo Data Designer](https://github.com/NVIDIA-NeMo/DataDesigner): separate structured attributes from generated prose; validate fields independently. Their released distributions are not customer facts.
- [MatrAIx](https://arxiv.org/abs/2608.04205): separate scenario, persona and verifier; adherence is not predictive accuracy.
- [Concordia](https://github.com/google-deepmind/concordia): preserve interaction state across turns without having a model invent product state.
- [Nubank's simulation paper, v1](https://arxiv.org/abs/2609.30137v1): isolate user simulations and production tool effects; use scenarios targeting observable failures. Its measured results do not transfer to a different implementation.
